Local SPM modules compile WITHOUT library evolution, so a struct's memory layout is baked into every consumer module at compile time. That mechanism is real. What was WRONG in this note originally was blaming SPM's incremental build for failing to recompile consumers — **retested 2026-07-25 on Swift 6.4 and it does not reproduce.**

**The retest.** In a clean worktree: `swift build --build-tests` to seed, md5 every `.o` under `.build/out/Intermediates.noindex/Modules.build/Debug`, add a stored property (`[String: Double]`) to `SalvageSite` in `UniverseModels` — changing the layout of `Planet`/`StarSystem` — rebuild, re-hash. Recompiled: `UniverseModels`, `UniverseModelsTests`, `GameServices`, `LocationsFeature`, `LocationsFeatureTests`, `NewStarMapFeature`, `NewStarMapFeatureTests`. Exactly the right closure. Then `swift test` on the three suspect products: **140 tests, 0 issues, no segfault**, with no `Package.swift` change and no `.build` clean.

**Why the original theory was wrong.** The suspicion was missing dependency edges: 10 targets `import` a local module they don't declare (`LocationsFeatureTests` and `NewStarMapFeatureTests` both `import UniverseModels` while declaring only `LocationsFeature`/`GameModels`/`GameDatabase`). That's true but harmless — a corrected audit (closure over declared deps) shows **every** such import is transitively reachable through a declared dependency, which is ordinary legal SPM, and swiftbuild invalidates across the full transitive closure, not just direct edges.

**Where the missing-edge theory DOES hold: the deprecated `native` (llbuild) backend.** In `.build/debug.yaml`, a target's compile command lists only its *directly declared* deps as inputs — `C.LocationsFeatureTests-*.module` has `LocationsFeature`/`GameDatabase`/`GameModels` swiftmodules and no `UniverseModels`, while `UniverseModelsTests` does list it. It still compiles because every built swiftmodule shares one directory on the import search path. So under `--build-system native` an undeclared-but-transitively-reachable import can go untracked, and invalidation has to arrive via the intermediate swiftmodule changing — which it needn't, since a non-resilient module doesn't encode its dependency's field offsets. That is almost certainly the toolchain the original crash was seen on. Swift 6.4 defaults to `swiftbuild`; `native` is deprecated.

**How to apply.** Do NOT reach for `rm -rf Modules/.build` on a segfault after a layout change — that ritual cost full ~100s rebuilds for nothing. Debug it as a real bug first. If a layout-shaped segfault ever does appear, check `swift build --build-system` isn't pinned to `native` before suspecting staleness. Real backtraces live in `~/Library/Logs/DiagnosticReports/swiftpm-testing-helper-*.ips` (parse the JSON, faultingThread frames) since `SWIFT_BACKTRACE` is disabled for the privileged test helper.

**Unrelated but adjacent, and confirmed still true:** synthesized `Decodable` ignores stored-property defaults — a missing key throws `keyNotFound` even for `var b: [String: Double] = [:]`. So adding a field to a type persisted as a JSON blob (e.g. anything inside the `StarSystem` blob in `systemDetails`) needs an explicit tolerant `init(from:)` or an Optional, or old blobs stop decoding. This is a data-compat concern, not a build concern.

**The Xcode app-run half is UNVERIFIED and still stands as written.** Adding `@State` stored properties to a PUBLIC SwiftUI `View` in a module (e.g. `nebulaConfig`/`nebulaParams` on `NewStarMapView`) changes the view's size; the app target kept the old smaller layout under Xcode's INCREMENTAL build, so `MainView.content` allocated too small and the init corrupted the heap. **Symptom:** `EXC_BAD_ACCESS` in `swift::RefCounts::incrementSlow` (an ARC retain) inside `ViewBuilder.buildBlock` — a wild address, not a nil. `BuildProject` reports success and the crash still happens. **Fix:** `rm -rf ~/Library/Developer/Xcode/DerivedData/<proj>-*/Build`, then a full rebuild (~80s vs the usual ~6s incremental confirms it recompiled). This goes through the `.xcodeproj`'s dependency on the package products — a different build system from `swift build` — so the retest above says nothing about it.
