As of the v2.1.1 upgrade (2026-07-09), the OpenAPI spec is version-tracked in `Modules/API/Sources/OpenAPI/`:
- `openapi-<version>.json` — pristine spec fetched from the server (untouched).
- `openapi-<version>-edits.json` — pristine + the local drift patches (this is what the generator consumes).
- prior versions' `-edits` files are kept for history (e.g. `openapi-2.0.1-edits.json`).
- `Modules/API/Sources/openapi.json` is a **symlink** → the active `OpenAPI/openapi-<version>-edits.json`. The swift-openapi-generator build plugin auto-discovers the file literally named `openapi.json`, so the symlink is what makes a version active.

To see exactly which local patches are applied: `diff` the pristine vs the `-edits` file for a version. Patches are strict, typed key additions only — the spec is kept strict, no `additionalProperties` relaxation ([[openapi-spec-drift-leniency]]).

Upgrade steps that worked: repoint the symlink to the new `-edits`, then `swift build --target API` + regenerate the diagnostic decorator ([[decode-diagnostics-decorator]]) because new operations (2.1.1 added `getV1Achievements` / `getV1AchievementsAchievementKey`) change the `APIProtocol` surface.

**Migrating the edits to a new version is a per-patch decision, not a blanket re-apply.** Diff pristine→`-edits` for the outgoing version to enumerate the patches, then for each one check whether the new pristine already covers it — the server does eventually adopt our fixes, and carrying a superseded patch forward means fighting the real spec. Retire a patch only on evidence: probe the live endpoint (`replicant raw GET …`, see the `probe-api` skill) and confirm the payload matches upstream's declaration. Insert carried-over patches at the same position in their parent object, so the new pristine↔`-edits` diff stays hunk-for-hunk comparable with the old one.

**File formatting is `json.dumps(obj, indent=2)` with the default `ensure_ascii=True` and NO trailing newline** — that reproduces the stored pristine files byte-for-byte. `ensure_ascii=False` differs (it is 10 bytes shorter on 2.3.3, from escaped non-ASCII in descriptions), and so does adding the trailing newline. Match it or the pristine↔`-edits` diff fills with noise that hides the real patches. Key order is the server's emission order, never sorted: `components.schemas` is not alphabetical, so a new schema goes beside its topical sibling (that is where `LocationEventResolutionResponseSchema` sits) or at the tail when it has none.

**A "null where the schema is not nullable" is NOT a decode failure in a response.** All 34 `required` lists in the spec sit on REQUEST schemas; no response property is required anywhere, so every generated response property is an Optional and `null` decodes to `nil`. Only two classes actually throw: an undeclared key under `additionalProperties: false`, and a genuine type mismatch. A live-payload validator that flags nullability buries the real drift under noise — one `GET /v1/devices` page produced 50 benign hits (`stowed_in_device_code`, `controller_device_code`, `attached_to_device_code`) and zero real ones. Same reason `owner`'s plain `$ref` on `DeviceStatusSchema` is safe despite arriving null.

**Migrating the patches is mechanical if you anchor them, not index them.** Walk the old pristine / old edits / new pristine trio together: a key we added that the new pristine now has is ADOPTED (compare the values — identical means retire it); one it still lacks is re-inserted immediately after the nearest preceding key that survives into the new object. Anchoring by neighbour rather than by numeric index is what makes upstream insertions (`has_ward` landing between `has_hub` and `region`) harmless. A value we changed replays only when the new pristine still holds the old value; anything else is a genuine three-way conflict and must be looked at by hand. On 2.5.1 that produced 36 carries, 2 retirements, 0 conflicts.

On the **2.5.1 upgrade (2026-08-21)**: no new or removed paths or schemas, so the decorator stayed at 89 operations. **Two patches retired** — upstream now declares `short_description` and `description` on `app_schemas_devices_DeviceStatusSchema`, byte-for-byte identical to ours and in the same tail slot after `created_at`, which is what the 2026-08-15 note predicted would happen. `owner` is still declared on no schema upstream and carried forward, now sitting after upstream's `description`. The other 34 carried at their original positions. Upstream's substantive changes: `has_ward` (non-nullable `boolean`) on both `StarItemSchema` and `CatalogueStarSchema`; `arrival_time` on `app_schemas_travel_TravelResponseSchema` — the very sibling our device-command `arrival_time` patch was typed from, and the device-command schema still lacks it, so that patch survives; `tags` and `exclude_tags` on `GET /v1/devices`, comma-separated patterns supporting `*` wildcards (`tags=auto:salvage:*` filters live, verified). `MessageSettingsSchema.subscribed`'s enum reordered a third time, cosmetic as ever.

**One patch ADDED 2026-09-06 for the v3.0.0 season — `environment` on `app_schemas_species_SpeciesSchema`**, a `$ref` to a new `app_schemas_species_SpeciesEnvironmentSchema` inserted at the tail after our `star_regions` patch, so both species patches sit contiguous in the pristine diff. Unlike every prior patch this one was found by **sweeping live payloads against the pinned spec, not by a throw** — the Civilisations screen was already broken on main and nobody had opened it. All 28 species carry the block and it is `additionalProperties: false`, so `CivilisationsClient`'s `getV1Species().ok.body.json` threw on every load. The eight keys (`biosphere`, `gravity`, `hydrosphere`, `oxygen`, `pressure`, `tectonic`, `temperature`, `toxicity`) are each a 2-element `[min, max]` array; **typed `number`, not `integer`, deliberately** — six of the eight are integral across all 28 species today, but `gravity` and `pressure` are already fractional and the terraforming docs describe fractional per-tick deltas on every attribute, so narrowing on 28 samples would arm a type error rather than retire one. Upstream declares neither `environment` nor `star_regions`, so both survive the next upgrade. `APITests/SpeciesResponseDecodingTests` pins it, and the pin bites at BUILD time (verified by deleting the property: `value of type 'AppSchemasSpeciesSpeciesSchema' has no member 'environment'`).

**The sweep is worth repeating on any season bump.** A `default`-only response and an undeclared key both stay silent until a user opens the screen. Validating live GET payloads against the pinned spec found this one, and found nothing else across 16 other endpoints the app calls — see `.scratch/v3-alteration-protocol/spec.md` for the full v3 gap list.

**One patch ADDED to 2.5.1 (2026-08-21) — `hub_bonus` on `app_schemas_devices_DeviceCommandResponseSchema`**, a nullable boolean inserted after `travel_type`. Found by a live throw, not by the diff: a Survey Run travel got `DecodingError.dataCorrupted: Path: hub_bonus. Additional properties are disabled, but found 1 unknown keys`. Typed by the sibling-schema rule — upstream declares `hub_bonus` as `{"type": "boolean", "nullable": true}` on `app_schemas_travel_TravelResponseSchema`, the same travel block the device-command schema mirrors, and still has not added it to the device-command one, so the patch survives the next upgrade. Same shape as the `arrival_time` patch of 2026-08-14 and the mine-response patches of 2026-08-12: the spec describes the payload correctly on the replicant-level schema and the device-command schema is simply missing the block. `APITests/DeviceCommandResponseDecodingTests.decodesTravelStartWithHubBonus` pins it.

**The throw cost three hours of stall, and the spec patch is only half the fix.** A response the client cannot decode throws AFTER the server has acted, and the op was recorded `.failed` — the one status `CommandGovernor` reads as "safe to re-POST" — so the retry six seconds later hit `Device is not in a star system` and stalled the run. Declaring the key retires this instance; the next undeclared field would do the same. See [[failed-means-never-sent]] for the classifier that makes the whole class survivable.

**`has_ward` is present-or-absent, never null**, exactly like `has_hub`: 94 of 21,722 catalogue stars carry it and all 94 are `true`; a survey probe returns `false` on all 20 rows. Upstream's non-nullable declaration is accurate, and it is plumbed through both `StarsClient` mappers into `StarItem`/`Star` as `hasWard` (see [[star-flag-plumbing-path]]).

On the **2.5.0 upgrade (2026-08-10)**: three new paths — `POST /v1/devices/{device_code}/retrieve`, `GET /v1/tutorials`, `GET /v1/tutorials/{slug}` — so the decorator grew 86 → 89 operations. **The first upgrade where upstream adopted NONE of our patches**: all 21 carried forward at their original index in their parent object, nothing retired. Other upstream changes: a `TriangulateSchema` device command (`signature` + `target` `[x,y,z]`, `oneOf` 23 → 24), `flatpack` on `EnqueuePrintSchema`/`PrintRequestSchema`, `linked_device` on four device schemas, and doc-only edits to the `/v1/events` `cursor` (it now documents an `archive:<id>` form) and the `MessageSettingsSchema` enum order.

**`linked_device` was already live before the spec declared it** — `GET /v1/devices` returns it (null on all 20 rows probed) while `DeviceListItemSchema` is `additionalProperties: false`, so the 2.3.3 strict decoder was throwing on the device list until this upgrade. Upstream shipping the field is what fixed it, not a patch of ours.

**Six more patches ADDED to 2.5.0 (2026-08-12), from a live `mine` throw on `POST /v1/devices/{device_code}`:** the mine response sends `site`/`designation`/`location_type`/`salvage_type`, none declared on `app_schemas_devices_DeviceCommandResponseSchema`, so every mine command threw with 4 unknown keys. The types were not guessed — **upstream's own `app_schemas_mining_ReplicantMineResponseSchema` already declares the identical payload** (it serves the replicant-level mine endpoint), so the device-command schema was simply missing a block the spec describes correctly elsewhere; `designation` and `belt` are marked there as DEPRECATED aliases of `site` and `location`, which is why the response repeats each value twice. Two more keys came off that same comparison rather than off the throw: `availability` and `density` are `nullable` on the mining schema and were not on ours — a salvage-site mine (`location_type: "salvage"`) sends both null, so the next throw was already armed and would have been a *type* error, not an unknown-key one. Both widened; neither changes a generated Swift type (an optional property is `String?` either way), and nothing reads them off the typed struct anyway — `Mining.swift` pulls the whole block out of an untyped container. `APITests/DeviceCommandResponseDecodingTests` pins both site classes so a future upgrade dropping these patches fails a test instead of a live command. **When a payload throws, grep the spec for a sibling schema describing the same shape before typing anything by hand.**

**One patch ADDED 2026-08-14 — `arrival_time` on `app_schemas_devices_DeviceCommandResponseSchema`** (nullable string, inserted after `total_distance_ly`), and it is the first patch whose type came from the LIVE swagger rather than from our pinned pristine: upstream has since declared `arrival_time` on `app_schemas_travel_TravelResponseSchema`, the same shape the device-command travel block mirrors, so the sibling-schema rule below was answered by fetching `https://api.replicant.space/swagger/openapi.json` and grepping it. Upstream has NOT added the key to the device-command schema, so this patch survives the next upgrade. **Total live drift past pinned 2.5.0 as of 2026-08-14 is two schemas and nothing else** — no new/removed paths or schemas, `TravelResponseSchema` gaining `arrival_time`, and `MessageSettingsSchema`'s `subscribed` enum reordered again (cosmetic, as in 2.5.0). `APITests/DeviceCommandResponseDecodingTests.decodesTravelStartWithArrivalTime` pins it, and the pin bites at BUILD time rather than as a red test: drop the patch and the generated type loses `arrivalTime`, so the test file no longer compiles.

**Three patches ADDED 2026-08-15 — `short_description`, `description`, `owner` on `app_schemas_devices_DeviceStatusSchema`**, all at the tail after `created_at`. **`GET /v1/devices/{device_code}` returns TWO shapes and only one of them was known**: a device you OWN answers with the full status blob (now also carrying the two catalogue-copy fields), and a device you DON'T own answers with a seven-key public view — `device_code`/`location`/`owner`/`short_description`/`description`/`device_type`/`features`, no `status`, no `replicant_code`. Both decode against the same `DeviceStatusSchema`, which is `additionalProperties: false`, so the foreign view was throwing on three unknown keys and the owned view on two. Types: the live swagger already declares `short_description`/`description` as non-nullable `{"type": "string"}` in exactly that tail position, so ours match byte-for-byte and retire cleanly on the next upgrade; `owner` is declared on NO schema upstream, and its `{name, replicant_code}` shape is exactly `app_schemas_accounts_ReplicantBriefSchema`, so it is a plain `$ref` (the house style — 26 plain `$ref` properties, zero `allOf` wrappers). **The copy fields are ABSENT, never null**, on most devices — of eight owned devices probed only an `ftl_slingshot` and a `replicant_matrix` carried them — which is why non-nullable-with-no-`required` is right. The device LIST is unaffected: `GET /v1/devices` rows are `DeviceStatusSchema` too and send neither field. `APITests/DeviceStatusResponseDecodingTests` pins all three shapes.

**Two patches ADDED for 2.5.0, and they are the first ones found by reading the diff rather than by a live throw:** both `tutorials` operations declare only `default`, which is the [[undocumented-success-response-throws]] shape — a 200 decodes against the strict error schema and every success throws. Neither endpoint has an app caller yet, so nothing would have failed loudly; the trap was armed for whoever wired the first one. Both now declare a `200` against four new `app_schemas_tutorials_*` schemas modelled on live probes of all seven tutorials and three detail payloads (the list item carries `available`/`order`/`total_steps`, the detail carries `steps[]` instead — they are different shapes, not a subset). Style follows our one prior added schema: `additionalProperties: false`, properties alphabetical, **no `required`**, so every generated property is optional and call sites coalesce. **Worth making routine: scan every NEW path in an upgrade for a responses block that is `default`-only.**

On the **2.3.3 upgrade (2026-07-27)**: no new/removed paths or schemas, so the decorator stayed at 86 operations — all 17 upstream changes were inside existing definitions. One patch retired: upstream now declares `has_hub` on `StarItemSchema` (as non-nullable `boolean`; a live survey probe returns `false`, never null), so ours was dropped. `name` on `StarItemSchema` was **kept** — the survey endpoint still doesn't send it and upstream still only declares it on `CatalogueStarSchema`, so the same rare-named-system reasoning as 2.3.2 applies. It had to move to the end of the property list because upstream took over the slot after `entry_point`. The other 18 patches carried over at their original positions.

Worth knowing from 2.3.3: **upstream narrowed `eta_seconds` `number`→`integer` on six schemas, plus `BlueprintSchema.print_time`** — so the generated Swift types went `Double?`→`Int?`. Nothing broke, because the app either coerces (`Int(schema.printTime ?? 0)`) or reads the value out of an untyped container (`Printing.etaSeconds` via `["eta_seconds"]?.numberValue`). Live probes confirmed the narrowing is accurate (eta values 2779/28/1371/86, 31 integral `print_time`s). Note the *sibling* fields are still genuinely fractional — `route_eta_seconds` (27.8) and a route leg's `time_seconds` (45.4) — so don't generalise the narrowing to them. 2.3.3 also added `region` to both star schemas (survey returns `"solzone"`), `hosting_replicant` to `DeviceStatusSchema`, `quantity` to `EnqueuePrintSchema`, `tag`/`untagged` query params on `GET /v1/devices`, and a `cursor` param + `422` on `/v1/events/stream`. **`region` is not yet plumbed into `StarItem`** — the mappers in `StarsClient` ignore it.

On the **2.3.2 upgrade (2026-07-26)** that retired two patches: the server now declares `/v1/stars`'s `200` natively as `app_schemas_stars_CatalogueResponseSchema`, replacing the hand-written `app_schemas_stars_FullStarCatalogueSchema` + response block we had added. Note the catalogue row got its **own** schema (`CatalogueStarSchema`), distinct from the per-replicant `StarItemSchema` the survey endpoints still use — so `StarsClient` needs a second `StarItem.init(schema:)` overload, and the catalogue genuinely carries no `explored`/`has_life` (14,066 stars probed; only `has_hub`/`name` beyond the common fields). The other 20 patches carried over unchanged. 2.3.2 also added `/v1/leaderboards/colony_planet` + `/v1/leaderboards/colony_moon`, which grew the decorator 84 → 86 operations.
