`NewStarMapFeature` (Modules/NewStarMapFeature) is the raw-Metal reimplementation of the star map, ported from a standalone prototype (its `README.md`/`HANDOFF.md` live in the module root and carry the full design rationale + invariants). It coexists with the old SceneKit `StarMapFeature` — surfaced as a separate **"Stars (New)"** Catalog sidebar entry (`SidebarItem.starsNew`) so both can be viewed during the port. Goal: it eventually *replaces* `StarMapFeature`.

Structure: pure-logic + domain files (Star, Galaxy, FTLMesh, DataFilter, RelevanceField, LabelEngine, Ship, TurntableCamera, Math) are portable Swift and unit-tested (51 Swift Testing tests, all passing). Metal-specific: Shaders.metal, StarFieldRenderer, LabelTextureCache, MetalStarView. See [[metal-spm-integration]] for the SwiftPM build wiring.

TCA conversion (per user request "convert @Observable to TCA where feasible"): the old `@Observable Selection` class became `NewStarMapFeature` reducer State (`selectedStar`, `activeFilterName`). The imperative camera/renderer stays behind the `MetalStarView` `NSViewRepresentable`; the AppKit input layer forwards outcomes as actions (`starFocused`/`starDived`/`selectionCleared`/`homeRequested`/`dataFilterCycled`). Mirrors the existing StarMapFeature's "reducer owns declarative intent, controller stays imperative" split.

Live data: wired to the same persisted `UniverseModels.Star` table the SceneKit map reads. `NewStarMapView` observes `@FetchAll(UniverseModels.Star.order(by: \.createdAt))`, maps each row to the module's render `Star` via `Star.init(surveyed:)` (in `LiveStar.swift`), and feeds `[Star]` to `StarFieldRenderer(mtkView:stars:)` — which no longer calls `Galaxy.generate()` (kept only for tests/fallback). Renderer rebuilds when the terrain changes; empty table → placeholder ("survey from the Stars view"). DB→domain gaps filled by stand-ins (resources=0, life=bool→.complex/.none, scan from explored/fullyScannedAt, hasFTLRelay from entryPoint!=nil, temperature=class-band midpoint, age=deterministic FNV hash of designation) — these are the fields the HANDOFF marks "game supplies real values."

**Body-view lighting + SEAMLESS drill (DONE, 2026-07-13 — was the two deferred polish items). The body drill is now the galaxy→system move one level deeper.** Key requirement from the user: NO disconnect — the planet you see in the system view is the same size/position as in the body view, it zooms in from where it orbits, and moon orbits emerge/recede into the planet exactly as planets do with the star.

(1) **Lighting:** the body sun was at the real star position, which — after scaling the planet up — fell *inside* it (planet unlit, moons lit as if the planet were the sun). Fix: keep the true star DIRECTION but put the light far out via `bodySunPosition(planet:starIndex:distance:)` = `planet + normalize(star−planet)·(frameWorldRadius·40)`; recomputed every frame as the planet orbits. Body draw + halo read it via `PlacedBody.sun`.

(2) **Pause the orrery instead of tracking (user's call — simpler than per-frame camera follow, which was tried and removed).** `orbitClock: Float` is the orbit-animation time (feeds `orbitAngle`, `currentOrbiterWorldPosition`) — an ACCUMULATOR that advances with `dt` EXCEPT while `orreryIsBody || departing != nil`, when it FREEZES. So on drill-in the planet + siblings hold still (planet centre is fixed → no camera-follow needed, no drift), and it resumes from the same phase on the way out (freeze/unfreeze never jumps). Consequence: moons don't orbit at body level (they still axis-spin via `u.time`, which is never frozen) — acceptable per the user. Surface spin/flares/belt all use `u.time`, NOT `orbitClock`.

(3) **Scale the planet UP to sun-sized (fixes tiny-value/clipping problems).** `enterBody`: `orreryScale = star.worldRadius / centralScene` so the settled central body is as big as the system star (≥ the sun's angular width), keeping world units comfortable (star.worldRadius∈[0.05,0.17]) — no more Rp-tiny scale. Seamless start WITHOUT a pop: the central body's radius GROWS from `bodyCentralStartRadius` (= the planet's system rendered radius `Rp = planet.displayRadius_system · systemScale`, always < star.worldRadius since sizeFraction<1) to its full body radius across `bodyProgress` (lerp in `placedOrreryBodies`, applied only when `centralBody != nil`, i.e. the body layer). At `bodyProgress=0` central=Rp at the frozen planet position = the departing system planet → continuous; then it grows as the camera dives. `camera.near` still pulled to `dFinal·0.02` in `enterBody` (restored via `saved.near` in exit) so a near-side moon can't clip when dollied to the floor on a small star. `bodyCentralStartRadius` cleared to 0 at settle-to-system.

(3b) **The drilled planet is ONE continuous body, never cross-faded (user was seeing a double).** It's drawn exactly once and stays FULLY OPAQUE — only its SIZE changes (`uCentral.orreryAlpha = orreryReveal` in `encodeOrreryLayer`, independent of the layer's fade). The SYSTEM layer SKIPS it via `excludeID = bodyPlanetID` (renderer state, set in `enterBody`, persisted in `StarMapViewpoint` with `bodyCentralStartRadius` for restore, cleared at settle-to-system); `placedOrreryBodies`/`orreryPips` take `excludeID`, and `PlacedBody.isCentral` flags the central so the body/atmosphere loops give it `uCentral`. On drill-in the body layer's central IS the planet (opaque, growing Rp→full); on zoom-out the departing body central is it (opaque, shrinking full→Rp), then hands to the system planet at Rp on settle. Because it's a procedural impostor the same material renders at any size (no fidelity loss — the user's "scaled-down version" idea). The opaque central ALWAYS writes depth (`placedBody.isCentral || writesDepth` in the body loop) even on a departing layer — else the OTHER layer's additive orbit rings + HZ band, drawn afterward, composite THROUGH the planet (reads as dim/transparent on zoom-out); only the fading moons skip depth writes. And `encodeOrreryLayer`'s early-out `guard alphaReveal > 0.001` MUST also allow `model.centralBody != nil` — otherwise in the last sliver of a zoom-out (alphaReveal→0 but bodyProgress not yet exactly 0, so `departing`/`bodyPlanetID` uncleared and the system layer still excludes the planet) the opaque central gets skipped and the planet vanishes for exactly one frame (position-independent → every planet).

(4) **Cross-fade plumbing:** eased clock `bodyProgress` (0=system,1=body) + `departing` snapshot (`DepartingOrrery`) render BOTH orreries in one frame via `encodeOrreryLayer(...)`. TWO decoupled uniforms: `orreryReveal` = orbit/scaffold grow-out+POSITIONS (per layer: `isBody ? bodyProgress : systemProgress` — so MOONS emerge/recede with bodyProgress while system planets stay put), `orreryAlpha` = per-layer FADE (`systemProgress · layerOpacity(isBody:)`). Sun (focused field star) fades+shrinks to a point via `bodyReveal` in `star_vertex` (fieldDim→0, ceiling mix→maxAngularSize, extra fieldShrink). Departing layer draws with no depth write. `orreryIsBody` persisted in `StarMapViewpoint` (restore settles `bodyProgress`, `bodyContext=nil` → static until next drill). **Remaining/deferred:** central-body pip at body level; real moon orbital radii (index-stepped); retire debug "Transition ×" slider; cut over to replace SceneKit `StarMapFeature`.
